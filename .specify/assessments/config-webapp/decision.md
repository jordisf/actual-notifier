# Decision: Live-reload for actual-notifier configuration

- **Slug**: config-webapp
- **Decided**: 2026-09-23 (revised same day after explicit maintainer clarification)
- **Verdict**: go — Concept **Option C** (web admin panel), scoped to LAN/VPN-only exposure with username+password authentication
- **Artifacts reviewed**: intake.md, research.md, problem.md, concept.md

> **Revision note**: this decision originally rendered a narrower go on Option A (listener hot-reload only), on the grounds that the two headline pain points from intake.md did not hold up under repo inspection. When presented with that finding, the maintainer explicitly confirmed the goal is broader than the confirmed listener gap: **avoid ever needing to enter the server to change configuration, with everything actionable from a web UI**, restricted to LAN/VPN, with username/password authentication. That is Concept Option C, not Option A. This revision supersedes the original scorecard/rationale below it was replacing; superseded reasoning is preserved in git history of this assessment.

## Verdict & Rationale

**Go — Concept Option C**, constrained to: **LAN/VPN-only** network exposure (no exposure beyond the maintainer's own network/VPN) and **username + password authentication** required for all actions. The maintainer explicitly confirmed both constraints after being shown the security trade-offs, and explicitly restated the goal as "todo debe ser accionable desde la UI web" — i.e., avoiding server access entirely for configuration, which Option A alone does not deliver.

This supersedes the original Option A go. The original rationale (small appetite, zero new attack surface) remains factually correct, but the maintainer's actual requirement is broader than the single confirmed listener gap: they want one web-based control surface for configuration in general, not just a fix for the one narrow gap research surfaced. That is a legitimate scope the maintainer is entitled to choose, once the security trade-offs (new inbound-adjacent service, need for auth, secrets handling) were made explicit and accepted.

**Scope note carried to `/speckit-specify`**: problem.md's current Non-Goals list "any browser/web UI" and "editing SMTP or Actual Budget credentials or the cron schedule" as out of scope — those non-goals are **now superseded by this decision** for whatever is confirmed in-scope below. `/speckit-specify` should treat this decision.md, not the original problem.md Non-Goals section, as authoritative for scope; problem.md itself has not been rewritten and should be read historically (it documents the narrower gap that research first confirmed, not the maintainer's full requirement).

## If go — Handoff to `/speckit-specify`

- **Problem**: Today, changing any part of `actual-notifier`'s behavior (Telegram bot settings, SMTP, Actual Budget connection, monitored categories, report schedule) requires the maintainer to SSH/enter the server and hand-edit `.env` and/or `crontab.txt`, plus in some cases a manual container restart. The maintainer wants a single web-based control surface so no configuration change ever requires direct server access.
- **Chosen approach**: Concept Option C — a small web admin panel in a **new, dedicated container** (not embedded in the existing notifier image), reachable **only from the maintainer's LAN/VPN** (no public exposure), gated by **username + password authentication**, through which configuration is viewed and changed. Secrets (SMTP password, Actual password, Telegram bot token) are **displayed masked by default, with a per-field "show" toggle** in the UI — never silently plaintext-by-default, matching the lesson from the `Telegram.md` incident. Changes must apply without requiring a manual container restart.
- **Schedule mechanism (analysis)**: the maintainer is indifferent to storage/syntax/mechanism, so pick the smallest-diff option consistent with the rest of this decision (small, no new dependency, no cross-container network calls). Two real options were considered:
  - *(a) Replace OS cron with an in-process scheduler* inside `notifier-cron` (e.g. a long-running loop re-checking a cron expression from the shared store, similar in shape to `notifier-listener`'s poll loop). Rejected as the primary recommendation: it turns `notifier-cron` from a one-shot-per-tick process into a new long-running service, a materially bigger architectural change than needed just to make the schedule editable.
  - *(b, recommended) Keep OS cron and `crontab.txt` exactly as-is architecturally; the panel container writes cron-syntax lines directly into the same host-mounted `crontab.txt` file (already shared via bind mount, per `docker-compose.yml`) — just mount it `:rw` for the panel instead of `:ro`. Add a small poll loop to `notifier-cron`'s existing `entrypoint.sh` (a few lines of `sh`, no new dependency) that checks `crontab.txt`'s mtime on an interval and re-runs `crontab /app/crontab.txt` when it changes — applying the new schedule without a container restart.* This keeps cron itself, its syntax, and its container role completely unchanged; the panel is free to offer a friendlier "every day at HH:MM" input and translate it to a cron line, or just accept raw cron syntax directly, since the maintainer has no preference either way.
- **In scope**: a web UI in its own container, reachable only on LAN/VPN, protected by username/password login with masked+revealable secret fields; viewing and editing Telegram config (bot token, group id, category allow-list, poll timeout), SMTP config, Actual Budget connection config, `NOTIFICATION_EMAIL` recipients, and the report schedule (via the `crontab.txt` + mtime-watcher mechanism above); changes take effect without a manual container restart.
- **Out of scope**: multi-user/multi-operator accounts (single shared login is assumed unless stated otherwise); public/external (non-LAN/VPN) access; anything beyond configuration (no report-content/business-logic changes); replacing OS cron with an in-process scheduler (considered and rejected above).
- **Success metrics**: (1) the maintainer never needs to open a terminal/SSH session to the server to change configuration; (2) all configuration changes — including previously listener-only and previously cron/SMTP/Actual ones — apply without a manual `docker compose restart`; (3) no new incident of a secret exposed in plaintext (in git or otherwise) is introduced by the panel's storage or transport.
- **Resolved during decision (no longer open)**: secrets are masked-with-reveal-toggle (not hidden-only, not plaintext-by-default); the panel runs in its own new container; the schedule keeps `crontab.txt` + OS cron, applied live via a small mtime-watcher in `notifier-cron`'s `entrypoint.sh` (Option b above) rather than replacing cron with an in-process scheduler.
- **Resolved during decision (round 2)**:
  - **Auth storage & recovery**: username and a **bcrypt-hashed** password (not reversible encryption) are stored in `.env`. If the stored hash is **empty**, the panel allows one login without a password but **immediately forces setting a new password** before any other action is available — this is a one-time recovery flow, not a standing passwordless bypass (rejected: an always-available blank-password bypass would undermine the LAN/VPN + mandatory-auth requirement already confirmed). Username and password can subsequently be changed from within the panel itself.
  - **Validation**: the panel validates configuration before persisting/applying it (e.g., test SMTP send, test Telegram bot token/group id) rather than silently accepting and only failing later on the next report/poll cycle.
  - **Schedule UX**: a friendly, deliberately narrow input with exactly three modes — "every X minutes", "every X hours", or "once a day at HH:MM" — no arbitrary/atypical cron expressions exposed. The panel translates the chosen mode to a single cron line under the hood, written via the `crontab.txt` + mtime-watcher mechanism already decided above.
